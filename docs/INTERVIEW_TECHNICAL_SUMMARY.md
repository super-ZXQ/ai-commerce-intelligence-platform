# 面试技术总结：以代码与实测为依据

**为什么选择LangGraph？** 这里有真实分支与可恢复步骤：知识问答只检索，数据问题读schema并生成SQL，混合问题两者都做；生成、校验、执行失败最多纠错一次。`agent_core/runtime.py`把状态、分支和停止条件显式化，单测可注入模型与执行器，还能复用在API和Streamlit。并非因为用了图就宣称具备任意自治规划能力。

**为什么使用确定性路由？** 五类固定意图下零模型Token、稳定、可解释。新独立30题仅56.7%准确率、53.1% Macro-F1，说明口语、模糊表达、多意图仍有限制。现有curated100%不能代表真实泛化。B/C真实调用认证失败，不能声称规则优于LLM，也不能根据Mock决定切换生产路由。

**为什么需要SQL AST？** 关键词黑名单无法理解CTE、别名、子查询、字段位置和查询结构。`sql_safety.py`解析作用域并验证schema，拒绝通配、跨库、未授权列、标识明细、危险/未知函数、复杂语法和恒真JOIN；COUNT(DISTINCT user_name)与SELECT user_name有不同授权含义。新增55条安全用例覆盖允许与拒绝路径。AST不等于完整成本优化器，仍需执行时限和数据库权限。

**为什么还要只读账号？** 应用校验可能存在遗漏，数据库必须独立阻止写入和读账本payload。bootstrap撤销旧权限，迁移后只给orders业务列SELECT；生产启动核验SHOW GRANTS。真实MySQL测试证明聚合可执行，UPDATE/DELETE/CREATE与账本读取均被拒绝。开发回退需要显式开关，不能作为生产容错。

**如何避免RAG缓存污染？** Key包含完整query、k、threshold、规范化metadata Filter、共享knowledge_version；返回值深拷贝，失效世代防止进行中的旧检索回填。完整规范化Chunk的SHA256解决后半段修改遗漏，删除失效ID、重复ID去重、版本推进解决更新一致性。API词面检索也按源内容指纹刷新。Chroma多步构建还不是原子快照，应承认维护窗口限制。

**如何保证订单幂等性？** event_id唯一索引负责最终幂等，账本与orders在同一事务提交；版本号拒绝旧事件，FOR UPDATE保护已有订单状态。ID使用AUTO_INCREMENT，历史卷有Alembic迁移。READ COMMITTED避免不存在订单的间隙锁竞争。实测50/100不同订单并发、20次重复事件、同订单退款/取消、锁超时重试与回滚；这不是无限吞吐保证。

**如何评估Text-to-SQL正确率？** 新20题冻结query、参考SQL和拒绝标签，在真实MySQL独立schema中执行候选与参考结果，比较列身份、排序与数值误差，并统计执行率、结果正确率、纠错、错误、Token和P50/P95。36行合成数据有退款/取消/跨年场景，可复现且不把真实用户明细发给模型。此次提供方401导致没有模型候选成功返回，指标N/A；单元/数据库测试不能代替模型能力结果。

**做了哪些A/B实验？** 路由A规则、B确定性安全拦截后LLM、C规则优先且对无明确数据标记的兜底调用LLM；三者共享100/25/10/30题，C配对使用B的响应而非独立重复调用。真实检索比较词面、BGE/Chroma和RRF Hybrid：新18题上Hybrid未提升Recall、拒答更弱，未启用，Reranker未引入。原heldout后来部分失败模式已进入安全加固，所以本次新增独立测试集，不能继续把旧集叫完全独立。

**当前限制是什么？** 模型凭据认证失败，B/C与SQL能力待验收；小规模审计者编写集未做人类双盲标注；API/UI检索器不同；BGE阈值下无答案拒答不足；RFM完整快照是单worker进程内缓存；Chroma上游漏洞告警未清零；旧Git材料疑似凭据待核对；没有运行完整生产Docker栈、公网HTTPS或分布式负载测试。不能把本次正确性修复写成未经测量的性能收益。
